### 11.2 最根本的盲点：派生 CASE 被排除在事实校验之外

`scripts/validate_stage4_cases.py:140-170` 的 Canonical 一致性检查写法是：

```python
corpus = "\n".join(body for name, (meta, body) in parsed.items() if name.startswith(f"{pid}_"))
```

`parsed` 收录了 cases 目录下的全部文件，但过滤条件是 `startswith("P001_")`——**`CASE001_…` 不满足该前缀，因此四个跨项目 CASE 文件从未进入任何一个项目的语料**。它们只通过"元数据 schema + 文件名 + 合成声明 + `## 关联` 段 + 无工程噪声 token"这几项检查。

这正是 §4.2 中全部 7 处二次生成漂移能存活的原因：**派生文件不受事实校验约束**。

### 11.3 校验器的文字级/数值级盲点汇总

```text
1. 只校验 ID 是否存在         → 不校验 ID 后面的名称
2. 只校验字段是否存在         → 不校验字段的值是否自相矛盾
3. 只校验 Canonical 数值是否"出现过" → 不校验它是否挂在正确的事件/日期/科目上
4. 只校验项目级合计           → 不校验台账与叙述层的科目级一致
5. 只校验台账日期是否升序     → 不校验同一业务链内部的先后（申请≤比选≤签约≤到货）
6. 只校验字符串是否出现        → 不校验正文内部加总是否闭合
7. 派生 CASE 不参与事实校验
8. sources/ 与 CLAIM_PROVENANCE 的 section / claim_scope / notes 三列无人读取
```
